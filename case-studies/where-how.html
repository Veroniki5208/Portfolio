Where-How: show me where to click

A browser extension that reads your screen and places a visual pointer directly on the element you need — designed for elderly users and anyone dropped into an unfamiliar interface without a map.

My Role
Product designer & builder — sketches, PRD, and the extension itself
Status
Working prototype — core loop live on real sites, single-step queries only
Platform
Browser extension (Chrome / Edge, MV3)
Primary users
Adults 60+, and anyone on an unfamiliar interface

The Problem

Support content exists. The gap is that it lives somewhere else.

Organizations pour resources into help centers, FAQs, and tutorial videos. But task abandonment stays high among non-technical users. The issue isn't the existence of support — it's that support lives outside the interface. Users have to read an instruction, then hunt for what it's describing on their specific screen, right now.

A redesign makes it worse. A user who knew exactly where to find their lab results last month is completely lost after a portal update. Existing documentation lags by weeks. For users who rely on family members or support phone lines to navigate these systems, every interface change is a real cost.

"How do I cancel my subscription?" and "Where is the add textbox button in Google Docs?" are the same question. Someone knows what they want to do but can't locate it. Most support gives them more text. Where-How gives them a pointer on the actual screen.The insight
User Research

Two users, one problem, different stakes

Primary research (interviews and observation) is planned as the next step. What follows is grounded in secondary research and the formative insights that shaped the PRD.

BackgroundRetired teacher. Uses a laptop daily for email, a healthcare portal, and video calls with family.
Tech comfortLow-moderate. Comfortable with Gmail. Struggles with anything that looks different from last time.
Key frustration"Every time they update the website I have to call my daughter to find where things moved."
Where-How use caseFinding lab results after her healthcare portal redesigned its navigation.

Secondary persona: Daniel, 34

BackgroundMarketing manager who just switched from HubSpot to a new CRM. High tech comfort in his usual tools.
Key frustration"The onboarding video doesn't match what I'm actually seeing on screen."
Where-How use caseFinding where to set up automation rules in a CRM he's never used before.
01
The support content gap is structural. It's not a volume problem — users context-switch between reading instructions and executing them, a cognitive load that compounds on an already-unfamiliar interface.
02
UI changes create repeat confusion. Where-How reads the live DOM, not pre-authored content, so it's always current even after a redesign.
03
"Where" and "how" are the same question. Users rarely ask what a button does — they ask where it is and how to do a thing. Both resolve to a screen location plus a plain-language explanation.
04
Visual guidance beats text for spatial tasks. Pointing at something is faster and more accurate than describing it.
The Concept

One question. One circle. No hunting.

The core interaction is deliberately minimal. The user opens the extension, types a plain-language question, and a red circle appears on the exact element they need — on the actual live page, not a screenshot or diagram. A short tooltip explains what the element does and what to do next.

Where-How works on any site with no integration required. It reads the live DOM, identifies interactive elements, and uses an LLM to match the user's query to the right one. If it's not confident in the match, it says so — a wrong pointer is worse than no pointer.

Where-How points, the user clicks. No automation in v1. Trust has to be earned before the tool takes action on someone's behalf — especially for elderly users on sensitive sites like healthcare portals.Design principle

What the demo shows: asking Where-How to find the link-insert button in Google Docs — it correctly highlights the toolbar icon. Then, asking it to locate the trash folder in Gmail after the sidebar is collapsed behind "more labels" — it correctly finds it once expanded, and the highlight box tracks the element as the sidebar scrolls.

What's worth noticing: when asked about recovering a deleted email — a multi-step task, not a single element — it didn't fabricate an answer. It said there wasn't a single button for that. That refusal is a deliberate design choice: a wrong pointer is worse than no pointer.

Feature Requirements

What v1 needs to do — and what it doesn't

PriorityFeatureWhat it does
P0Natural language inputUser types a plain-language question. No special syntax required.
P0Live DOM readerExtension reads the current page's live DOM to identify interactive elements, labels, and structure.
P0Element matching via LLMQuery and DOM representation sent to an LLM, which returns the best-matching element and a plain-language explanation.
P0Visual pointer overlayA red circle and directional arrow overlays the matched element. Non-destructive — disappears on dismiss.
P0Plain-language tooltip1–3 sentence explanation near the element: what it does and what to do next.
P1Low-confidence fallbackIf the extension isn't confident in its match, it says so instead of pointing to the wrong element.
P1Multi-element disambiguationIf multiple elements could match, lists them with short descriptions and lets the user choose.
P1Session-only privacyNo queries or DOM snapshots stored beyond the active session. No account required in v1.

Progress

Where the project actually is, phase by phase

1
Phase 1 — Validate the concept. Still open: interviews with adults 65+ navigating real interfaces; a paper-prototype test of the "red circle on screen" metaphor. Deferred: voice input decision, waiting on user research, not blocking the build.
2
Phase 2 — Technical prototype: can the core mechanism work? Yes, with real limits. Done: MV3 extension scaffolded (manifest, background service worker, content script, overlay CSS, options page); content script reads and structures the live DOM into a numbered list of clickable elements; DOM output wired to an LLM for element matching; tested on Google Docs and Gmail with correct highlights and correct "no such element" responses; fixed a bug where the highlight box went stale on scroll — it now re-tracks the element's position every animation frame. Not started: measuring match accuracy systematically across a larger set of sites and queries.
!
Known limitations. Single-step only — it can point to one element, but can't yet guide a multi-step task. Free-tier LLM rate limits, with no retry logic yet. Capped at ~150 DOM elements per page for prompt-size reasons.
3
Phase 3 — Usability testing. Recruit 5 participants from the primary persona group (adults 65+); run moderated sessions on 3 real-world tasks across 2 websites; measure against the success metrics above, then iterate.
Reflection

What building first, then writing the PRD, taught me

✓
What I learned — building first told me what to scope. I found the real seam — single-target "where is X" questions work well, multi-step "how do I recover this" questions don't — by hitting it during testing, not by predicting it on paper. That limitation is now in the PRD as a stated non-goal for v1, not a surprise.
?
What I'm uncertain about — whether the accuracy bar is achievable at scale. The LLM correctly identified real elements and correctly declined when nothing matched, on the pages I tested. 85% pointer accuracy is still the target, but I've only stress-tested a handful of sites and queries, not enough to know if that number holds.
◆
PM lens — open questions are part of the deliverable. I listed 5 open questions in the PRD that I don't have answers to yet. A PM who pretends everything is resolved before research is done is just making things up. The questions are honest work.
